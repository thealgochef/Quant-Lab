## RA-01 · medium · S14 binds `executed_trade_table_id` by assertion; the frame it stratifies is never tied to that artifact

- Contract: plan §3.7 ("S14 … binds the table artifact ID/hash in its own identity"; verified bytes reuse, different bytes fail closed); §3.1 last bullet (refuse a caller-supplied frame/hash that differs from the verified artifact); kickoff §10 "identity projection".
- File:symbol: `src/alpha_lab/agents/data_infra/ifvg/ml/regime_stratification_service.py:ChildStratificationInputs.executed_trade_table_id` (98–109), `build_regime_stratified_reports` (263; 342 `trades=child.trades`, 352, 358–359, 419–420), `_publish` (304–314); `ml/regime_stratified_strategy.py:build_cohort_descriptive_body` (225; body 350–351); `ml/regime_stratified_contracts.py:CohortDescriptiveBody` (394–447).
- What is wrong: the service does not import `load_executed_trade_table` / `project_executed_trades`. `child.executed_trade_table_id` is copied verbatim into the body and into `source_metric_refs` (`tuple(sorted(set(refs)))` — no load, no hash check). The body binds `executed_trade_table_sha256(ordered)` — the hash of the *caller's* normalized frame — next to an artifact id that nothing relates to it, and the artifact's own `executed_trade_table_sha256` (projection bytes) is not bound at all. The pairing is correct only because the pipeline caller (`regime_report_stage._child_table_evidence`) happens to take both from one verified load; the invariant lives in the caller, not in the seam that mints the immutable report.
- Reproduction: with the lane fixture of `tests/agents/data_infra/ifvg/test_regime_stratification_evidence.py`, persist two executed-trade tables A and B (`save_executed_trade_table`), then call `build_regime_stratified_reports` with `ChildStratificationInputs(trades=<B's frame>, executed_trade_table_id=<A's id>, …)`. A `cohort_descriptive` report persists whose body names table A and hashes B's rows; no refusal.
- Minimal resolution: in `build_regime_stratified_reports`, when `child.executed_trade_table_id is not None`, exact-load it from `inputs.root` and require `executed_trade_table_bytes(project_executed_trades(child.trades)) == loaded.table_bytes` (or source `trades` from the loaded artifact and drop the caller frame); bind the artifact's `executed_trade_table_sha256` in `CohortDescriptiveBody` beside the normalized-frame hash (re-mints report ids, which §3.1 permits). Post-fix: the reproduction refuses; the S14 pipeline test still produces identical reports across a double run.

## RA-02 · medium · `RegimeNetRAccounting` accepts an arithmetically impossible body

- Contract: plan §3.5 (definitions persisted "verbatim"); kickoff §10 "immutable reuse" (persisted evidence must be self-consistent, not merely well-typed).
- File:symbol: `ml/regime_stratified_contracts.py:RegimeNetRAccounting._coherent` (328–391); `CohortDescriptiveBody._coherent` (419–447).
- What is wrong: the validator checks key-set equality, the count sum, and the null/reason pairings only. It never recomputes `abs_net_r_mass`, `assigned_net_r_total`, the shares, the top share, the signed fractions, or the `works_only_in_regime` predicate from `net_r_by_regime`, and never requires `works_only_in_regime_id ∈ net_r_by_regime`. `CohortDescriptiveBody` mirrors two scalars and two totals but never checks `trade_count_by_regime[r] == strata[regime r].executed_trades`.
- Reproduction (ran against the worktree; accepted without error):
  `RegimeNetRAccounting(trade_count_by_regime={0:3,1:2}, net_r_by_regime={0:5.0,1:3.0}, assigned_trade_count=5, unassigned_trade_count=0, unassigned_net_r=0.0, assigned_net_r_total=-99.0, abs_net_r_mass=0.0, abs_net_r_share_by_regime=None, signed_contribution_fraction_by_regime={0:0.1,1:0.9}, top_regime_abs_net_r_share=None, works_only_in_regime=True, works_only_in_regime_id=7, works_only_in_regime_reason=None, zero_denominator_reasons=("zero_abs_net_r_mass",))`.
- Minimal resolution: recompute inside `_coherent` (tolerance 1e-12): mass = Σ|net|, total = Σ net, shares = |net|/mass with identical keys, top = max(shares), signed = net/total, `works_only_in_regime_id` must be the unique positive regime, `works is None ⇒ unassigned_trade_count > 0`; in `CohortDescriptiveBody`, per-regime counts must equal the regime strata's `executed_trades`. Post-fix: the body above is refused; `regime_net_r_accounting` output still validates (`test_thin_regimes_count_in_concentration_but_not_in_reportability`).

## RA-03 · medium · `works_only_in_regime` is null on any unassigned trade, and true for a single assigned regime

- Contract: plan §3.5 — "true only when [assigned total > 0, exactly one regime > 0, every other ≤ 0, unassigned == 0]; **otherwise false, or null … when unassigned trades prevent the claim**".
- File:symbol: `ml/regime_stratified_strategy.py:regime_net_r_accounting` (149–222; 197–205).
- What is wrong: `if unassigned_count > 0: works = None` is evaluated before the assigned-side predicate. When the claim is already false on the assigned side, unassigned trades did not "prevent" it, yet the persisted flag is null. Probe results: two positive regimes + one unassigned trade → `None / incomplete_assignment_accounting`; assigned total negative + one unassigned → `None`. Real populations essentially always contain unassigned trades (`panel_warmup`, `no_oos_assignment`, `candidate_as_of_missing`), so the persisted flag will be null in practice and a report can never state `false`. Separately, a single assigned regime with positive net R yields `True, id=0` (probe) — a vacuous concentration claim (the R6.1 code required ≥ 2 regimes; §3.5's wording admits the vacuous case but the class docstring does not warn of it).
- Reproduction: `regime_net_r_accounting(net_r=pd.Series([1.0,2.0,0.5]), clusters=np.array([0,1,-1]), valid=np.array([True,True,False]))` → `works_only_in_regime is None`.
- Minimal resolution: `assigned_claim = total > 0 and len(positive) == 1`; `works = assigned_claim if unassigned == 0 else (None if assigned_claim else False)`; set the reason only when null; persist `assigned_regime_count` (or require ≥ 2) so a vacuous single-regime truth is visible. Post-fix: extend `test_works_only_in_regime_claim_requires_complete_assignment_accounting` with the two-positive + unassigned case expecting `False`.

## RA-04 · medium · The F-10D enum guard mis-types container fields (latent false refusal on six identity-bearing fields)

- Contract: plan §3.9 F-10D ("pass enum members into enum-typed payloads").
- File:symbol: `search/identities.py:_enum_annotation` (243–251), `FrozenContract.model_copy` (265–278).
- What is wrong: `_enum_annotation` walks `get_args()` of *any* generic, so `tuple[Enum, ...]` resolves to the Enum and the guard then demands `isinstance(<tuple>, Enum)`. Probe over all 284 `FrozenContract` subclasses importable from `ifvg` + `propsim`: six fields affected — `PipelineSemanticSpecPayload.stage_plan`, `TradePathArtifactPayload.capabilities`, `TradePathBundlePayload.bundle_capabilities`, `PropRulePathRequirement.required_path_capabilities`, `PropRulePathRequirement.accepted_fidelity_classes`, `PathCapabilityReport.available_capabilities`. A lawful `model_copy(update={"stage_plan": (QuantLabPipelineStage.…,)})` raises `TypeError`; a tuple of raw strings is refused only as a side effect (no element check), and `Mapping[str, Enum]` / nested generics would be mishandled the same way. No current `src/`, `tests/`, or `scripts/` call site updates these six fields (grep), so the defect is latent, not breaking. `Enum | None` is handled; no union of two enums exists; `GeneratedProfileCapability.status` is a `Literal`, so `tests/agents/ifvg_search/test_orchestrator.py:531`'s raw-string update is unaffected.
- Reproduction: `spec.model_copy(update={"stage_plan": spec.stage_plan})` on any `PipelineSemanticSpecPayload` → `TypeError: … is enum-typed (QuantLabPipelineStage)`.
- Minimal resolution: use `typing.get_origin`: treat only bare `Enum` and `Enum | None` as scalar-enum fields; for `tuple[Enum, ...]` validate each element; otherwise pass through. Post-fix: a test that a tuple-of-members update succeeds and a tuple-of-strings update is refused.

## RA-06 · minor · §3.4 invariants not fully validated (invalid-row linkage, protocol column on load, assignment self-consistency)

- Contract: plan §3.4 ("For an invalid row, retain … row ID, candidate/panel ID, fold, partition, protocol and applicable fit reference"; "Validate on build, save, verified load, and downstream consumption").
- File:symbol: `ml/regime_contracts.py:validate_assignment_rows` (528–660), `_ASSIGNMENT_ROW_INVARIANT_COLUMNS` (421 — no `row_id`/`candidate_id`); `ml/regime_store.py:load_regime_fit_assignments` (487–524).
- What is wrong: (a) invalid rows are checked only for null outputs + a registered reason — `row_id`/`candidate_id` may be null and `partition` may be `None`/`"x"` on a fit-kind or model-facing row; (b) the loader re-checks `regime_fit_id` and `fold_index` against the envelope but not `resolved_regime_protocol_id` (persist-time `_bound_assignments` only); (c) no internal consistency of a valid row: `assigned_distance == distances[local] == min(distances)`, `assignment_margin == d2 − d1 ≥ 0`. ## RA-07 · minor · Candidate as-of identity conflates "unparseable" with "null" and does not record the stage on the candidate grain

- Contract: plan §3.3 ("an unparseable non-null timestamp remains a hard error"; "the source hash represents null deterministically").
- File:symbol: `ml/regime_oos_assignment.py:candidate_as_of_source_hash` (611–617, `errors="coerce"`), `_as_of_ns` (260–274); `ml/regime_executor.py:execute_regime_protocol` (229–234).
- What is wrong: on the candidate grain the as-of frame is only hashed — `_as_of_ns` (the hard-error path) never runs — so a garbage non-null anchor is silently represented as `None` in `candidate_as_of_source_hash`, indistinguishable from a true null. On the panel grain the same coerce runs after the rule already raised, so it is latent there. Additionally, the candidate grain hashes the anchors of `candidate_as_of_stage` but the payload records no stage (`panel_context=None`): the same output bytes get a different id per stage and the provenance of the hashed instants is unreadable from the artifact.
- Reproduction: candidate-grain observations with `entry_ts_utc="not-a-time"` for one candidate → `execute_regime_protocol` succeeds; the payload hash equals the one produced with `entry_ts_utc=None`.
- Minimal resolution: hash through `_as_of_ns` (raise on unparseable non-null); record `candidate_as_of_stage` for the candidate grain or hash only candidate ids there.

## RA-08 · minor · Typed sidecar reasons inferred from exception text

- Contract: plan §3.8 (typed sidecar probe/load contract; "sanitized typed failures").
- File:symbol: `search/executed_trade_table.py:probe_executed_trade_table` (302–319).
- What is wrong: `except Exception as error: message = str(error); reason = "envelope_identity_mismatch" if "does not match directory" in message … else "manifest_hash_mismatch"`. The reason S02 records in `row["explanation"]` and S15 reports is a substring heuristic: a pydantic message containing "failed verification" is typed as a hash mismatch, and every unmatched exception — including `OSError` — becomes `manifest_hash_mismatch` rather than `unexpected_io_error`. Fail-closed in all branches, so evidence integrity holds; reason fidelity does not.
- Reproduction: corrupt `envelope.json` of a persisted table so that `load_verified_envelope` raises a `ValidationError` whose text contains "failed verification" → reported as `sidecar_hash_mismatch`.
- Minimal resolution: raise `SidecarLoadError` with the reason at the point of detection inside `load_verified_envelope` (or classify by exception type: `SearchStoreError` subclasses / `ValidationError` / `OSError`).
